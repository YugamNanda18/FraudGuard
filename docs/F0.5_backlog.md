### E1 — BOE Ingestion Pipeline

**E1-001** | Prioridad: P0 | Puntos: 5
Como desarrollador del sistema, quiero un cliente HTTP que descargue legislacion consolidada de la API BOE para alimentar el corpus RAG con normativa actualizada.
Criterio de aceptacion: El cliente descarga correctamente documentos via `GET /legislacion-consolidada` con filtros por materia, maneja paginacion, y persiste respuestas en formato JSON. Tests unitarios con mocks de la API.
Dependencias: Ninguna

**E1-002** | Prioridad: P0 | Puntos: 3
Como desarrollador del sistema, quiero un cliente para la API de sumarios del BOE para detectar nuevas disposiciones relevantes publicadas cada semana.
Criterio de aceptacion: El cliente consulta `GET /boe/sumario/{fecha}`, filtra disposiciones por materias relevantes (fraude, blanqueo, PBC, servicios de pago, IA), y genera lista de nuevas disposiciones a indexar.
Dependencias: E1-001

**E1-003** | Prioridad: P0 | Puntos: 3
Como desarrollador del sistema, quiero mapear los codigos de materia del BOE relevantes para fraude bancario usando la API de datos auxiliares para filtrar descargas de forma precisa.
Criterio de aceptacion: Documentado el mapeo de codigos de materia (materias, ambitos, departamentos) relevantes para: PBC/FT, servicios de pago, proteccion de datos, IA, derecho penal economico.
Dependencias: Ninguna

**E1-004** | Prioridad: P0 | Puntos: 8
Como desarrollador del sistema, quiero un extractor de texto que parsee los documentos del BOE (HTML/XML) y los limpie mediante NLP para obtener texto legal estructurado y limpio.
Criterio de aceptacion: Extrae texto de documentos BOE manteniendo estructura (titulo, articulos, disposiciones, anexos). Elimina markup, headers/footers repetitivos, y caracteres especiales. Mantiene numeracion de articulos y referencias cruzadas intactas.
Dependencias: E1-001

**E1-005** | Prioridad: P0 | Puntos: 8
Como desarrollador del sistema, quiero un chunker semantico que divida el texto legal por articulo/seccion para que cada chunk mantenga coherencia juridica completa.
Criterio de aceptacion: Chunks delimitados por fronteras de articulo/seccion (no fixed-size). Cada chunk incluye metadata: ley, articulo, fecha publicacion, fecha consolidacion, estado consolidacion. Chunks entre 200-2000 tokens con overlap contextual (titulo de ley + capitulo).
Dependencias: E1-004

**E1-006** | Prioridad: P0 | Puntos: 5
Como desarrollador del sistema, quiero generar embeddings de los chunks legales con un modelo multilingue optimizado para espanol legal para alimentar el vector store.
Criterio de aceptacion: Embeddings generados con modelo multilingue (multilingual-e5-large o BGE-M3). Benchmark de calidad de embeddings en queries legales en espanol (cosine similarity >0.8 para queries sinonimas). Batch processing eficiente.
Dependencias: E1-005

**E1-007** | Prioridad: P0 | Puntos: 5
Como desarrollador del sistema, quiero un pipeline de ingestion orquestado que ejecute de forma automatizada: descarga, extraccion, chunking, embedding, y carga en vector DB.
Criterio de aceptacion: Pipeline end-to-end ejecutable con un comando. Logs detallados de cada fase. Manejo de errores con retry. Metricas: documentos procesados, chunks generados, tiempo total. Idempotente (no duplica documentos ya procesados).
Dependencias: E1-001, E1-004, E1-005, E1-006, E2-001

**E1-008** | Prioridad: P1 | Puntos: 5
Como desarrollador del sistema, quiero un scheduler que ejecute la ingestion semanalmente de forma automatica para mantener el corpus RAG actualizado.
Criterio de aceptacion: Cron job o scheduler (APScheduler/Celery Beat) ejecuta pipeline semanal. Notificacion de exito/fallo. Dashboard de estado de ultima ingestion.
Dependencias: E1-007

**E1-009** | Prioridad: P1 | Puntos: 5
Como desarrollador del sistema, quiero indexar normativa EU clave (AML, PSD2, AI Act) desde EUR-Lex como complemento al BOE.
Criterio de aceptacion: Al menos las 6 directivas/reglamentos EU del BRD (N-003 a N-005, N-006, N-009, N-011) indexadas y accesibles via RAG. Metadata incluye referencia DOUE.
Dependencias: E1-007, E2-001

### E2 — RAG System

**E2-001** | Prioridad: P0 | Puntos: 5
Como desarrollador del sistema, quiero configurar Qdrant como vector store para almacenar y consultar embeddings de normativa legal con hybrid search nativo.
Criterio de aceptacion: Qdrant desplegado via Docker con colecciones: `boe_legislation` (dense + sparse), `eu_regulation`, `session_{tenant_id}`. Soporta insert, query, delete. Filtrado por tenant_id y metadata (ley, fecha, materia). Hybrid search (dense + BM25 sparse) nativo. Tests de integracion con datos reales del BOE.
Dependencias: Ninguna

**E2-002** | Prioridad: P0 | Puntos: 8
Como desarrollador del sistema, quiero implementar hybrid search (dense + BM25 sparse) para maximizar la precision del retrieval de normativa legal.
Criterio de aceptacion: Retrieval combina busqueda semantica (embeddings) con busqueda lexica (BM25). Ponderacion configurable entre dense y sparse. Soporta queries en espanol e ingles.
Dependencias: E2-001

**E2-003** | Prioridad: P0 | Puntos: 5
Como desarrollador del sistema, quiero un reranker que reordene los resultados del retrieval para mejorar la precision de los documentos entregados al LLM.
Criterio de aceptacion: Reranker (cross-encoder o similar) aplicado sobre top-k resultados del hybrid search. Mejora medible en precision@k vs sin reranker. Latencia del reranking <500ms para k=20.
Dependencias: E2-002

**E2-004** | Prioridad: P0 | Puntos: 3
Como desarrollador del sistema, quiero una interfaz `search_boe` reutilizable por todos los agentes para consultar el RAG de normativa legal.
Criterio de aceptacion: Funcion/tool `search_boe(query, k, filters)` con parametros: query (texto), k (top-k configurable, default 10), filters (ley, materia, fecha). Retorna chunks con metadata, score de relevancia, y fuente completa. Interfaz consistente usada por Harvey, Louis, Jessica, Mike, Rachel.
Dependencias: E2-002, E2-003

**E2-005** | Prioridad: P1 | Puntos: 8
Como desarrollador del sistema, quiero evaluar la calidad del RAG con RAGAS para garantizar que el retrieval cumple el umbral de calidad requerido.
Criterio de aceptacion: Framework RAGAS configurado con metricas: Faithfulness, Answer Relevancy, Context Precision, Context Recall. Benchmark de 100+ preguntas sobre normativa de fraude bancario con ground truth. Score >0.8 en todas las metricas.
Dependencias: E2-004

**E2-006** | Prioridad: P1 | Puntos: 5
Como desarrollador del sistema, quiero versionado del corpus RAG para poder rastrear que version se uso en cada respuesta y hacer rollback si es necesario.
Criterio de aceptacion: Cada ingestion genera snapshot inmutable con version_id. Metadata por chunk incluye version_corpus, fecha_ingestion, estado_consolidacion. Rollback ejecutable en <5min. Normativa derogada marcada pero no eliminada.
Dependencias: E2-001, E1-007

### E3 — Agent Framework

**E3-001** | Prioridad: P0 | Puntos: 8
Como desarrollador del sistema, quiero una clase base `FraudAgent` que encapsule la logica comun de todos los agentes (system prompt, tools, memoria de sesion, manejo de errores) para evitar duplicacion.
Criterio de aceptacion: Clase abstracta con: carga de system prompt por personalidad, registro de tools, gestion de historial de conversacion, manejo de errores estandarizado, logging estructurado. Todos los agentes heredan de esta clase.
Dependencias: Ninguna

**E3-002** | Prioridad: P0 | Puntos: 8
Como desarrollador del sistema, quiero implementar el grafo de orquestacion con LangGraph para gestionar el flujo entre Donna y los sub-agentes.
Criterio de aceptacion: StateGraph con nodos: Donna (router), Harvey, Louis, Jessica, Mike, Rachel. Edges condicionales basados en clasificacion de Donna. Estado compartido con contexto de sesion. Soporte para transferencia de agente mid-conversacion.
Dependencias: E3-001

**E3-003** | Prioridad: P0 | Puntos: 5
Como usuario, quiero que Donna analice mi mensaje y me derive automaticamente al especialista correcto para no tener que saber cual agente necesito.
Criterio de aceptacion: Donna clasifica correctamente >90% de los casos en primera derivacion. Categorias: fraude transaccional (Harvey), compliance/regulatorio (Louis), investigacion de redes (Jessica), red teaming (Mike), data engineering (Rachel). Fallback: pregunta al usuario si confianza <0.7.
Dependencias: E3-002

**E3-004** | Prioridad: P0 | Puntos: 5
Como desarrollador del sistema, quiero definir system prompts con personalidad diferenciada para cada agente para que mantengan su identidad durante toda la conversacion.
Criterio de aceptacion: Cada agente tiene system prompt unico que define: personalidad (tono, estilo, nivel de formalidad), dominio de expertise, tools disponibles, formato de respuesta. Personalidad se mantiene consistente durante conversacion multi-turn (>10 turnos sin drift). Idioma adaptado al del usuario (ES/EN).
Dependencias: E3-001

**E3-005** | Prioridad: P0 | Puntos: 5
Como usuario, quiero que los documentos que subo se indexen y esten disponibles como contexto para todos los agentes de mi sesion.
Criterio de aceptacion: Upload de CSV, JSON, PDF, TXT. Documentos indexados en <30s. Disponibles para todos los agentes de la sesion. Eliminados al cerrar sesion (por defecto). Limite: 100MB por archivo.
Dependencias: E3-002

**E3-006** | Prioridad: P1 | Puntos: 5
Como usuario, quiero que si mi caso cruza dominios los agentes colaboren automaticamente para no tener que repetir informacion.
Criterio de aceptacion: LangGraph orquesta transferencia de contexto entre agentes sin perdida de informacion. Ejemplo: Harvey detecta fraude → Louis genera SAR → Jessica investiga red. Historial y documentos compartidos entre agentes en la misma sesion.
Dependencias: E3-002, E3-005

**E3-007** | Prioridad: P0 | Puntos: 3
Como desarrollador del sistema, quiero validar ADR-001 (LLM Strategy) con benchmarks reales para confirmar que Llama 3.1 8B clasifica >90% de intenciones correctamente como Donna router.
Criterio de aceptacion: Benchmark de 200 queries etiquetadas (40 por agente). Llama 8B Q4 via Ollama clasifica >90% correctamente. Latencia P95 <1.5s. Si falla threshold, documentar fallback a Claude API para Donna.
Dependencias: E3-003

**E3-008** | Prioridad: P1 | Puntos: 3
Como usuario, quiero poder valorar las respuestas de los agentes (util/no util) para que el sistema mejore con el tiempo.
Criterio de aceptacion: Cada respuesta permite feedback: thumbs up/down + comentario opcional. Feedback almacenado con: session_id, agent_id, query, response_id, rating, comentario. Datos disponibles para analisis de calidad.
Dependencias: E3-002

## 4. Definition of Done (DoD)

Una historia se considera **TERMINADA** cuando cumple TODOS los criterios siguientes:

### Codigo
- [ ] Codigo implementado siguiendo convenciones del proyecto (PEP 8, type hints, docstrings)
- [ ] Sin deuda tecnica conocida sin documentar (si existe, Issue creado)
- [ ] Linting pasado sin errores (ruff)
- [ ] Type checking pasado (mypy)

- [ ] Tests unitarios escritos (coverage >= 80% del codigo nuevo)
- [ ] Tests de integracion si aplica (interaccion entre componentes)
- [ ] Tests de seguridad si aplica (prompt injection, sandbox escape, cross-tenant)

### Seguridad
- [ ] Sin secretos hardcodeados (API keys, passwords)
- [ ] Input validation implementada
- [ ] Audit log integrado para acciones relevantes

### Documentacion
- [ ] Docstrings en funciones/clases publicas

- [ ] ADR creada si se toma decision arquitectural

### Review
- [ ] Code review aprobado por al menos 1 revisor
- [ ] @code-critic gate pasado (revision de arquitectura, seguridad, rendimiento)

### Despliegue
- [ ] Funcionalidad demostrable en entorno de desarrollo
- [ ] No rompe funcionalidad existente (regression tests pasan)
